The one-page version

Realm Raiders is a strategy game for Android phones. You build a castle on an island, create a 3D General, and raid other islands. Five AI "officers" advise you. The result of every raid is written to the Monad blockchain, so anyone can check that nobody cheated.

What was built

  • The phone app: 17 landscape screens with a base-builder HUD, an isometric island in a code-drawn forest with pinch zoom, troops and buildings modelled in 3D and baked into sprites on the phone, a 3D General creator, synthesised sound effects and original background music. All art is made by code; none of it was downloaded.
  • Gems and Auto Mode: an in-game currency earned only by playing, spent on letting the officers run the realm under orders sealed on chain — every move checked and logged.
  • Play with Friends: on the same Wi-Fi, raid a friend while they watch live, fight a Live Duel on one shared seed (recorded on the new RealmDuels contract).
  • The battle engine: the rulebook for every fight. It gives exactly the same result on any phone or computer, which is what makes raids provable.
  • The game server: stores players and bases, re-checks every battle, runs the AI officers, and sends the blockchain transactions.
  • Five AI officers: General, Architect, Strategist, Night Captain and Intelligence Officer. They speak through a Qwen language model, but every answer is checked. If an answer fails a check, the officer uses its built-in rules instead.
  • Smart contracts on Monad: RealmLedger (bases, seeds, results, night and Auto orders), RealmBadges (achievements) and RealmDuels (Live Duel results). Each General is also registered as an ERC-8004 agent with an on-chain reputation.
  • The rest: an Android app package, a landing website, and a replay-checking tool anyone can run.

Old proofs stay true

A replay records which rules it was fought under. The v1 rules are frozen in code, and the server fixes a battle's version when it is committed, so a v1 army can never be scored against a v2 seed. The stability fingerprints (200 seeded battles hashed together) are pinned for both versions and checked in Node, Chrome and the Android WebView:

Auto Mode: orders, not trust

The officers act on a fixed 5-minute beat. Before anything happens, each move is checked against the sealed Auto Orders (raids per hour, minimum win chance, Gold reserve, what to upgrade first, strike back, storm-shield) and logged with logAutopilot under the session's own on-chain id. A refused move is written to the Auto Log with its reason — "Refused: upgrade Citadel to level 2 (would leave 1500 Gold, orders keep 1950)" — and nothing happens. A closed offline realm catches up on exactly the beats it missed.

Play with Friends: the replay is the battle

When you raid a friend, your phone streams the actions it applied every half second. Their phone runs the same deterministic battle a moment behind — so what they watch is exactly what the host then verifies. In a Live Duel, one commit-reveal locks a single seed for both commanders; both replays are re-simulated, the winner is decided by stars, then %, then time, and the result goes on chain (RealmDuels, verified on Sourcify).

Chapter 1

The game in simple words

The game is set in the Emberwake Isles, an original world: a cold northern sea of storm-cut islands, left behind when a sky-dragon fell and broke the old continent. Every lord wants ember, the glowing stuff that washes up on the shores.

You are a lord with one island. During the day you build and raid. At night you give orders and go to sleep, and your AI officers defend the island within those orders. In the morning you read what happened.

What makes it different

  • Every raid is provable. You don't have to trust the game's server; anyone can re-run a raid and compare it with the public record.
  • AI officers with real jobs. They plan raids by actually simulating them, check your walls, and write your reports, and they can't invent numbers.
  • The AI acts while you sleep, but only inside orders you sealed. Each action is logged against those orders.
  • No crypto knowledge needed. No wallet to set up, no gas to pay.
  • Works offline. With no server around, the whole game runs on the phone.

A new player's first ten minutes

  1. Tap Guest commander (or Google/email when set up).
  2. Style a 3D General, give them a name, and raise them. They get an on-chain agent ID.
  3. Land on the home island. The General says what to do first.
  4. Open Build and tap SAVE BASE. The layout's fingerprint goes on chain, so raids on you can be judged fairly.
  5. Tap ATTACK, swipe to Briarholt, and let the Strategist test three plans.
  6. Tap ATTACK! (the battle seed is locked on chain), watch or take control, and get a "Fair play verified ✓" result.
  7. In the evening, save night orders. Next morning, read the report.
  8. Turn on Auto Mode and let the officers play inside the orders you locked.
Chapter 2

Architecture: the big picture

The system has four big parts: the phone, the server, the AI model and the blockchain. Under them is a set of shared packages that run on both the phone and the server. That shared code is the key idea of the design.

Think of a football match with a referee. The battle engine is the rulebook, and the phone and the server each have an identical copy. Your phone plays the match. The server, as referee, replays it from your recording using the same rulebook. If the two copies of the rules agree, the result is stamped into a public notebook (the Monad blockchain) where nobody can change it. The AI officers are coaches who give advice, but they can only use numbers that really exist.

Why it is built this way

  • Fair raids without trusting anyone. Battles run on the phone, so they are smooth and work offline. Because the engine is deterministic (chapter 4), the server can re-run any battle and catch a faked result.
  • One codebase, two places. The game services (packages/core) run on the server and inside the app. With no server in reach, the whole game still runs on the phone.
  • No crypto knowledge needed. Players never see a wallet or pay gas. The server's relayer pays for the transactions, and players see a simple "Saved ✓" chip (on the live chain: "Monad ✓", which opens the explorer).
  • AI that can't break the game. Officers give advice and draft orders, but every answer is checked, and actions on your behalf must fit orders you sealed on chain (chapter 8).

Chapter 4

The battle engine

The engine is the heart of the game. Give it an island, an army, a seed and the list of your taps, and it plays out the whole battle, tick by tick. It runs inside the app (in a background Web Worker, so the screen never freezes) and on the server (in a pool of worker threads).

The one rule: same input, same answer, everywhere

Different phones can round decimal numbers slightly differently. Over thousands of steps, a tiny difference grows until one phone says "3 stars" and another says "2 stars". To prevent this, the engine never uses decimals. Distances, health and timers are all whole numbers: one tile is 1,000 units, and health is counted in thousandths of a point. Then every device gets exactly the same answer, like a recipe followed to the gram.

  • Its own dice. Randomness comes from a small built-in generator called sfc32, started from the battle's seed. Same seed, same "random" events.
  • No risky maths. No square roots, sines or decimal division. The engine has its own integer square root and a 16-direction compass. A test scans the engine's source code and fails if anyone uses Math.random, Math.sqrt, Date and similar functions.
  • Smart path-finding. Troops find their way with flow fields: picture water flowing downhill toward every target at once. Walls count as "expensive" ground, so troops go around them unless breaking through is shorter.
  • Fingerprints. The replay is hashed with keccak256, the same hash Ethereum and Monad use, so the contract can store it and anyone can compare.

Proof that it really is identical

/dev/simA hidden page (tap the sign-in crest 7 times) that runs 200 random battles and 3 recorded "golden" battles on the device itself.

The engine plays 200 battles with random seeds and combines all their results into one fingerprint. That fingerprint is stored in a test. It came out exactly the same in Node.js on the PC, in desktop Chrome, and inside the real Android app on the emulator (Android 17, Chrome 145 WebView).

Three recorded golden battles also replay to the same hash, with check-hashes every 100 ticks along the way. If someone changes the rules by accident, these tests fail at once.

Speed: a full battle takes about 12–24 ms to simulate. The War Room runs 3 plans × 50 battles = 150 practice battles in about 1.3 seconds on the server.

Chapter 5

How a raid is proven

A cheater could try two things: pick a lucky seed (re-rolling the dice until the battle goes their way), or send a fake result. The raid flow below blocks both.

The seed is a dice roll nobody can secretly choose. First the server puts a secret in a "sealed envelope" by publishing only its hash on the chain (commit). A few blocks later it opens the envelope (reveal). The final seed mixes that secret with a random number from the player and data from the blockchain block itself. The server can't change its secret after committing, and the player can't predict the block data. So neither side can pick a lucky seed alone.

The result can't be faked. The phone sends a replay, the list of what you tapped and when, not the result. The server re-runs it with the same engine. Only if the stars, percentage and hash match does it record the result on chain. The replay also carries a copy of the defender's base, checked against the hash that was sealed on chain before the raid.

BeforeThe War Room shows the target's base "Sealed in the Ledger ✓" before you can lock the seed.
After"Verified on Monad": seed locked, replay hash, server re-simulation, result recorded, reputation.

Anyone can check, not just the server

  • On the Profile screen, the verify button downloads a battle's replay and re-runs it on your phone.
  • On a computer, pnpm verify-replay <battleId> --chain re-simulates the replay and checks it against what RealmLedger stored for that battle: the seed, the base hash, the replay hash, the stars and the destruction %. A live raid passed all 5.

Chapter 6

The smart contracts on Monad

A smart contract is a small program stored on a blockchain. Once deployed, its code and data are public and nobody can quietly change them. Realm Raiders uses four of its own contracts plus the two official ERC-8004 registries, a shared standard for giving AI agents an on-chain identity and reputation.

Deployed and verified

The contracts were deployed to Monad testnet (chain 10143) on 3 November 2026, and RealmDuels on 4 November 2026. Their source code is verified on Sourcify (the verifier behind the MonadVision explorer): anyone can read the exact Solidity that runs at each address. Language models sometimes invent things. So each officer gets the real facts (your gold, the win rates from the practice battles, and so on) and must reply in a fixed format. A check then looks at every number in the reply. If a number doesn't appear in the facts, the reply is thrown away and the officer answers from its field manual, a set of written rules that always works. The screen tags those answers "(field manual)", so you always know which kind you got.

Which model, and how fast

  • The live officers use Qwen3 4B running locally through Ollama, so no API keys or cloud costs. A hosted Qwen can be plugged in with two settings and is tried first.
  • Qwen3 normally "thinks out loud" before answering, which took about 10 seconds. Switching that off (reasoning_effort: "none") and using the 4B model brought answers to 1.8–3.2 seconds, inside the 4-second budget.
  • The greeting, the briefing, the night draft and the War Room advice were answered live by the model during testing. The other officers fall back cleanly when the model is slow.

Chapter 8

Night defence

Orders, not trust

At night, rival lords send small raiding parties (troop space of 4 + 2 × their Citadel level, and no General) against your island. You are asleep, so your officers act for you, but only inside the orders you sealed.

09 Night ordersRepair first: walls, defences or resources. Gold kept in reserve: 45%. Strike back: yes. Storm-shield at 60%.
10 Morning ReportEach raid with stars and a DefenseRecorded proof. Each autopilot action is marked "within orders ✓".

The report also shows actions that were refused. For example, "Struck back at the raiders' boats (Citadel delta 1)" is refused because the orders only allow striking back at raiders whose Citadel is at most 0 levels above yours.

From the report, the Architect can apply a layout fix in one tap. The base is then "unsealed" until you seal it again.

In the live run, the night produced 2 DefenseRecorded and 4 AutopilotAction transactions on Monad (see the table in chapter 6).

How the screens are made

  • React 19 draws the menus, panels and chat bubbles. A small store holds the player's state and refreshes the home screen every 8 seconds.
  • Phaser 4 draws the island and the battle in isometric view (the diamond-shaped 2.5D look). Buildings, troops, arrows and effects are painted with code on a canvas.
  • The battle screen plays the engine's ticks as animation. The real simulation runs in a Web Worker, so the drawing stays smooth.
  • Every "✓" chip (for example SeedLocked ✓ 0xf180…8f8b) is a link to the transaction on the explorer. In offline mode it shows "mock".
  • The fonts are Lilita One (buttons and titles) and Nunito (text), with Cinzel kept for the logo; all are bundled open-licence fonts, so the app needs no internet for them.
  • Troops and buildings are Three.js models baked on the phone into sprite sheets (5 directions mirrored to 8, idle/walk/attack/death), cached in IndexedDB; without WebGL the game keeps its 2D drawings.

Small things that make it feel like a game

  • Coins float up when you collect, with a sound.
  • Stars "pop" in one by one on the result screen.
  • Officers show a typing shimmer while they think.
  • A red dot on an officer means they have news.
  • If the server is slow, a "Courier delayed" banner appears instead of an error.
  • A Share card on the profile makes a picture of your General and record to share.
Chapter 10

The 3D General, art and sound

No art was downloaded or bought. Every picture in the game is generated by code when the app runs. This keeps the game original and the app small (5.6 MB).

CreatorA 3D figure on a turntable, rebuilt live as you change options.
Same General, profileThe figure spins on its plinth above your rank and badges.

How the General is made

  1. Built from blocks. Three.js assembles head, body, cloak, shield and weapon from simple shapes. Your choices (body, head, hair, cloak, weapon, shield, colours and faction) are stored as a small checked "appearance" record.
  2. Fingerprinted. The appearance is hashed and stored with the General, so the same record always rebuilds the same figure.
  3. Portrait painted. The 3D figure is rendered once to a square image, used in the officer bubbles and the share card.
  4. Battle sprite baked. The figure is also rendered small from the battle camera's angle, so the General in the 2D battle matches your 3D one.

The rest of the art

  • Island and battle: buildings, walls, troops and effects are drawn with Canvas 2D shapes, in the colours of your faction.
  • Landing page: a 3D island with a castle, trees and a glowing sea.
  • Sound and music: taps, deploys, shots, explosions, coins, building, stars and the victory tune are made live with the Web Audio API, and so are two original background tunes (a calm one at home, a drum-driven one in battle; on/off in Settings). The APK ships no audio files.
  • App icon: a vector "adaptive icon" for Android.

An originality check (pnpm check:originality) scans all 285 source files for names, terms and asset paths from other games and fails the build if it finds any. The world, names and look are original to Realm Raiders.

Chapter 11

Online, offline and Android

Two ways to play

Because packages/core runs on the phone too, the offline realm is the real game, not a demo: the same rules, the same economy, and the same raid checks. It only swaps the database for an in-memory store (saved on the phone), the blockchain for a mock ledger, and the AI model for the field manuals.

Turning the web app into an Android app

  • Capacitor 8 wraps the built web app in a native Android shell (a WebView), giving a normal installable APK.
  • Portrait only, single window, an adaptive vector icon, and App Links, so links to the website can open the app. The website publishes an assetlinks.json file with the fingerprints of the signing keys.
  • Two builds: debug (7.1 MB, may talk to a plain-http server on the PC for testing) and release (5.6 MB, signed with a private release key kept outside the project folder).

Testing on a real Android system

A script (e2e-android/apk-playthrough.ts) uses Playwright to drive the installed APK on the Android emulator, through the app's own WebView: sign in → create General → seal base → War Room → raid → verified result → night orders → morning report → Auto Mode → profile. It took the screenshots in this report and checks that no page errors happen. It passed live (against the server and Monad) and offline.

Problems found only on the phone, and fixed: Android blocked plain-http calls from the app (allowed in debug builds only). The server refused the phone's PUT requests until its CORS settings listed them (a test now covers it). The WebView quietly switched image links to https, so images are now loaded as blobs. Portrait links pointed to "localhost", which is the phone itself, so they are now rewritten to the server's address.

Chapter 13

How it was built

The work followed the project guide (main_project/Project_Guide.md), which splits the game into 12 phases. Each phase ended with working, tested code before the next began. After phase 11 came the go-live step: deploying to Monad and play-testing the APK.

The building blocks used

ToolUsed for

React 19, Phaser 4, Three.jsScreens, the 2D isometric island and battle, the 3D General and boss.

How each phase was done

  1. Write the numbers first (game-data), then the rules (engine), with tests for every rule: walls block, sappers break walls, drakelings fly over, traps trigger, the rally works.
  2. Lock the rules down with golden replays and the 200-battle fingerprint, so later work can't change battles by accident.
  3. Build the game loop offline, then move the same services to the server and add the database and logins.
  4. Add the chain behind a switch: a mock chain for development and tests, and the live chain with a real relayer for Monad.
  5. Add the AI last, with a rule-based field manual written first, so the game never depends on the model being up.
  6. Play it on a phone, fix what breaks there, deploy, and play again live.

Keeping secrets safe

The relayer's private key, the session secret and the release-signing password live in files that git ignores (.env, keystore.properties), and the release key file sits outside the project folder. A pre-commit guard refuses any commit that contains them. None of them appear in this document.

Glossary

Blockchain: a shared public record that many computers keep in sync. Once something is written, it can't be quietly changed.
Monad testnet: the practice version of the Monad blockchain. Its coins have no money value, so it's safe for testing.
Smart contract: a small program that lives on the blockchain and follows its code exactly.
Transaction: one action sent to the blockchain, such as "record this result".
Gas: the small fee a transaction costs. The game's relayer pays it, not the player.
Relayer: the server's wallet, which sends transactions for players.
Hash: a short fingerprint of any data. Change one bit of the data and the fingerprint changes completely.
Seed: the starting number for the game's dice. Same seed, same rolls.
Commit–reveal: first publish the hash of a secret, then reveal the secret later. It proves you didn't change your mind.
Deterministic: always giving the same output for the same input, on any device.
Replay: a tiny recording of a battle's inputs (what was tapped and when), not a video.
Tick: one step of the battle clock, 1/20 of a second.
ERC-8004: a standard for registering AI agents on a blockchain, with an ID card and a reputation score.
Soulbound badge: a token that can't be sold or given away; it stays with the player who earned it.
Merkle root: one fingerprint that stands for a whole list, so any single entry can be checked later.
Sourcify verification: proof that the published source code is exactly what runs at a contract's address.
Monorepo: one repository holding several packages that share code.
API: the set of web addresses the app calls to ask the server for things.
WebSocket: an always-open connection, so the server can push updates instantly.
Web Worker: a background thread in the app, used to run battles without freezing the screen.
APK: the install file for an Android app.
Capacitor: a tool that wraps a web app into a native mobile app.
LLM: a large language model, the kind of AI that writes text. Here: Qwen3.
Ollama: a program that runs language models on your own computer.
